## Specific to this cluster (LabDA)

**Step 1 -- addresses**, reserved on 2026-10-03/04 in the LabDA Clusterbook:

```bash
for d in 223:edge-tt-test1 226:edge-tt-test1-play; do
  curl -s -X POST http://clusterbook.sthings-infra.4sthings.tiab.ssc.sva.de/api/v1/networks/10.100.136/reserve \
    -H 'Content-Type: application/json' \
    -d "{\"cluster\":\"${d#*:}\",\"status\":\"ASSIGNED\",\"create_dns\":true,\"ip\":\"10.100.136.${d%%:*}\"}"
done
```

`edge-tt-test1-play`'s DNS name is unused since the players' side moved to
`*.sthings-edge.com` (Hetzner record `*` → `10.100.136.226`).

**Step 9 -- the LabDA Vault issuer** (`lab/vault-issuer.yaml`, ClusterIssuer
`vault-pki-4sthings`): the k8s auth mount `edge-tt-test1-certmanager` on the
LabDA Vault and the Secret `cert-manager/vault-pki-ca`, once (again if the
cert-manager namespace is ever rebuilt):

```bash
env -u SSH_AUTH_SOCK dagger call -m github.com/stuttgart-things/blueprints/argocd@v3.6.2 \
  create-vault-kubernetes-auth \
  --cluster-name edge-tt-test1 \
  --kubeconfig-source-file <kubeconfig.enc.yaml> \
  --vault-env-file <vault-labda.enc.yaml> --sops-key env:SOPS_AGE_KEY \
  --auth-name certmanager --namespace cert-manager \
  --bound-service-account-names cert-manager --bound-service-account-namespaces cert-manager \
  --token-policies pki-issue-4sthings --token-ttl 3600 \
  --ca-secret-name vault-pki-ca
```

`vault-labda.enc.yaml` is stuttgart-things `secrets/envs/vault-labda.enc.yaml`;
`pki-issue-4sthings` is the policy the other LabDA mounts bind.

**The CoreDNS forward** (`lab/coredns-lab-zone.yaml`, k3s `coredns-custom`):
the node lists two resolvers and only `10.100.136.115` knows
`4sthings.tiab.ssc.sva.de`, so the zone is forwarded there (details:
[notes](../../docs/edge/notes.md)).
